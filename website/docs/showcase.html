Why this changes the game for Python logging

Traditional logging asks you to describe execution one disconnected line at a time — you thread request IDs through function signatures by hand, you scroll a 30-frame traceback to find the one line that's actually yours, and every polling loop floods the log forever. runtime-narrative asks a different question: what is the story of this execution? Wrap it in story()/stage() once, and correlation, diagnostics, and noise control come for free.

Traditional print() / loggingruntime-narrative
Correlating one request across functionsThread a request ID through every function signature and every log call by handNest story() calls — sub-stories auto-link via ContextVar, no threading, no new API
Understanding a failureScroll a 30+ frame traceback mixing your code with framework internalsOne pinpointed frame, a source snippet, and — in rich mode — the exact local values involved
Noisy polling loopsOne log line per iteration, foreverCoalescingRenderer collapses repeats into a single summary line
Explaining "why it broke"You reread the traceback and guessAn optional LLM analyzer turns the traceback into a plain-English cause and a targeted fix
Changing where output goesRewrite your logging callsSwap renderers — same events, any combination of console/JSON/SQLite/OTel/Prometheus/webhooks

2. Call tracing across functions, for free

Open a story() while another is already active — an API handler calling a DB helper, say — and it automatically becomes a linked sub-story: its own success/failure and duration, tagged with a short ID, indented by nesting depth, colored consistently per story family. No correlation ID to thread through the call, no manual span-linking.

[5752d4]'s story inherited [7a6211]'s renderers and diagnostics automatically and shares its root_story_id — this holds up under real concurrency for free, since asyncio.Task copies ContextVar state at creation. Details: Sub-stories & Log Capture.

3. Structured logs and a failure box, from one story()

NarrativeLogHandler folds ordinary logging.warning()/.error() calls into the same event stream as story()/stage() — one timeline instead of two. level_icons prepends any string (typically an emoji) per log level, no custom renderer required, and a failure still gets the full diagnostics box automatically.

4. No more flooded logs from polling loops

Status-polling loops — waiting on a pipeline, an upload, a job queue — are the classic source of log floods: one line per iteration, sometimes for minutes. CoalescingRenderer wraps any other renderer and collapses a run of identical back-to-back stages into a single summary line once it's clear they're repeating.

Without CoalescingRenderer

With CoalescingRenderer
45 iterations → 5 lines
▶ Stage started: Check Pipeline Status
✔ Stage completed: Check Pipeline Status (2.010s)
▶ Stage started: Check Pipeline Status
✔ Stage completed: Check Pipeline Status (2.005s)
'Check Pipeline Status' repeated 43 more times (45 total) over 90.400s (avg 2.009s/call)

The wrapped renderer still sees the first two occurrences in full — so it's visible that polling started — before collapsing the rest. Machine-consumption renderers like JsonRenderer or SqliteStoryRenderer should stay unwrapped for full fidelity. Details: CoalescingRenderer.
