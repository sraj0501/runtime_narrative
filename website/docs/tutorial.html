Tutorial: Your First Story

A hands-on walkthrough for people who haven't used runtime-narrative before. You'll take a plain, print()-based import script and grow it — one small step at a time — into something with automatic failure diagnostics, nested call tracing, multiple output formats, and a real test. ~20 minutes

Before you start

Python 3.9+ and pip install "runtime-narrative[console]" (the console extra gives you the colored terminal output shown below — everything still works without it, just in plain text). See Installation if you haven't already.

What you'll build

A tiny customer-import pipeline: load rows from a CSV, validate them, insert them. It's deliberately simple — the point isn't the pipeline, it's watching the same eleven lines of business logic gain progress tracking, structured failure diagnostics, nested tracing, and a test suite without ever being restructured.

Step 1 — Start with the plain version ~2 min

Here's the script before runtime-narrative touches it — three functions and a main(), instrumented the way most of us actually write a first draft: a few print() calls for progress, and whatever the interpreter prints if something goes wrong.

python
# import_customers.py
import csv

def load_csv(path):
    print(f"Loading {path}...")
    with open(path) as f:
        return list(csv.DictReader(f))

def validate_data(rows):
    print(f"Validating {len(rows)} rows...")
    for row in rows:
        if not row.get("customer_id"):
            raise ValueError("missing customer_id")

def insert_records(rows):
    print(f"Inserting {len(rows)} rows...")
    seen = set()
    for row in rows:
        cid = row["customer_id"]
        if cid in seen:
            raise ValueError(f"duplicate customer id: {cid}")
        seen.add(cid)
        # db.insert(row) -- pretend this writes to a real database

def main():
    rows = load_csv("customers.csv")
    validate_data(rows)
    insert_records(rows)
    print("Done.")

if __name__ == "__main__":
    main()

This works, but it has the three problems every logging setup eventually runs into:

  • The print() calls tell you a stage started, never how long it took or whether it actually finished.
  • If insert_records raises, you get Python's raw traceback — no indication of which stage was running, no structured way to tell "load failed" from "insert failed" in a log aggregator.
  • Nothing here composes: call this from a web request handler and a background job at the same time, and you have no way to tell their log lines apart.

Step 2 — Wrap it in a story ~3 min

Import story and stage, wrap the body of main(), and delete the now-redundant print() calls. The function bodies of load_csv, validate_data, and insert_records don't change at all.

python
# import_customers.py
import csv
from runtime_narrative import story, stage

def load_csv(path):
    with open(path) as f:
        return list(csv.DictReader(f))

def validate_data(rows):
    for row in rows:
        if not row.get("customer_id"):
            raise ValueError("missing customer_id")

def insert_records(rows):
    seen = set()
    for row in rows:
        cid = row["customer_id"]
        if cid in seen:
            raise ValueError(f"duplicate customer id: {cid}")
        seen.add(cid)

def main():
    with story("Import Customers"):
        with stage("Load CSV"):
            rows = load_csv("customers.csv")
        with stage("Validate Data"):
            validate_data(rows)
        with stage("Insert Records"):
            insert_records(rows)

if __name__ == "__main__":
    main()

Step 3 — Make it fail on purpose ~3 min

No code changes needed — just give customers.csv a duplicate customer_id so insert_records raises. This is the moment instrumentation earns its keep: instead of a bare traceback, story() catches the exception at the story boundary, builds a structured failure report, and then re-raises it.

Two things worth noticing:

  • The failure box already tells you the exact stage, the exact line, and the exact code that raised — without you writing any error-handling code.
  • Python's own traceback still prints after the narration. That's not a bug: by design, story() narrates and then re-raises, the same as a plain with/try block, so anything downstream (a web framework turning this into an HTTP 500, a task queue retrying the job) still sees the exception. If you own the whole call stack and want to stop there, story(..., suppress_traceback=True) does that — see story() for when that's (and isn't) a good idea.

Step 4 — Turn on rich diagnostics ~2 min

By default, diagnostics are lean: enough to locate the bug, with no runtime cost beyond reading the traceback. Add one keyword argument to see the actual variable values in scope when it failed:

python
with story("Import Customers", failure_diagnostics="rich"):
    ...

The same failure now includes a Locals section, sourced from the failing frame (and one enclosing frame):

text
  Locals (rich diagnostics):
    cid  = 'CUST-104'
    seen = {'CUST-101', 'CUST-102', 'CUST-103', 'CUST-104'}
    row  = {'customer_id': 'CUST-104', 'name': 'Priya Shah', 'email': 'priya@example.com'}

Rich mode automatically redacts anything that looks like a secret (keys containing password, token, api_key, cookie, and more) before it's ever captured — you don't have to remember to scrub credentials out of your own log statements. Full field list and every redaction option: Failure Diagnostics.

Step 5 — Trace a nested call, for free ~3 min

Split the insert logic into its own function that opens its own story():

python
def insert_into_db(rows):
    with story(f"DB: bulk insert {len(rows)} rows"):
        with stage("Open Connection"):
            conn = db.connect()
        with stage("Bulk Insert"):
            conn.insert_many(rows)

def main():
    with story("Import Customers"):
        with stage("Load CSV"):
            rows = load_csv("customers.csv")
        with stage("Validate Data"):
            validate_data(rows)
        with stage("Insert Records"):
            insert_into_db(rows)

Nothing was passed between the two functions to link them. Because insert_into_db's story() opens while Import Customers's story is still active (same call stack, same ContextVar context), it's automatically detected as a sub-story — its own success/failure and duration, but tagged, indented, and colored as part of the same family:

This is the same mechanism that makes a web request handler calling a database helper trace correctly with zero setup, and it stays correct under real concurrency — asyncio.Task copies context at creation time, so many callers sharing insert_into_db at once never cross-link into each other's tree. Step 6 — Send the same events somewhere else too ~2 min

A renderer is anything with a handle(event) method. Pass more than one and every event goes to all of them — nothing about load_csv, validate_data, or insert_into_db needs to change:

python
from runtime_narrative import story, stage, ConsoleRenderer
from runtime_narrative.renderer.json_renderer import JsonRenderer

with open("import_customers.jsonl", "a") as log_file:
    with story(
        "Import Customers",
        renderers=[ConsoleRenderer(), JsonRenderer(output=log_file)],
    ):
        ...

You still get the colored terminal output from Step 2, plus one compact JSON object per event written to import_customers.jsonl — ready for a log aggregator, with the full diagnostics payload (stack frames, source snippet, locals) included on failure:

text
{"event": "StoryStarted", "story_id": "9b31de...", "story_name": "Import Customers", ...}
{"event": "StageCompleted", "stage_name": "Load CSV", "duration_seconds": 0.002, ...}
{"event": "FailureOccurred", "error_type": "ValueError", "error_message": "duplicate customer id: CUST-104", ...}

Swap in SqliteStoryRenderer for a queryable database plus a CLI (runtime-narrative failures), or OtelRenderer for distributed tracing — same pattern every time. Full catalog: Renderers.

Step 7 — Write a test ~3 min

StoryRecorder is a drop-in replacement for story() in tests: it creates the story context, records every event, and gives you assertion helpers instead of parsing console output. The one rule: the code under test must call stage() directly, not open its own story() — which our main() already does.

python
# test_import_customers.py
from runtime_narrative import stage
from runtime_narrative.testing import StoryRecorder
from import_customers import load_csv, validate_data, insert_records

def run_import(rows):
    with stage("Validate Data"):
        validate_data(rows)
    with stage("Insert Records"):
        insert_records(rows)

def test_import_succeeds_on_unique_rows():
    rows = [{"customer_id": "CUST-101"}, {"customer_id": "CUST-102"}]
    with StoryRecorder("Import Customers") as r:
        run_import(rows)
    r.assert_stages_completed(["Validate Data", "Insert Records"])
    r.assert_no_failure()

def test_import_fails_on_duplicate_id():
    rows = [{"customer_id": "CUST-101"}, {"customer_id": "CUST-101"}]
    with StoryRecorder("Import Customers") as r:
        try:
            run_import(rows)
        except ValueError:
            pass
    r.assert_stage_failed("Insert Records", error_type="ValueError")

error_type is a string

error_type="ValueError" — a string naming the class, not the class itself. Full assertion reference: Testing with StoryRecorder.

What you just built

Starting from eleven lines of plain Python, you added: per-stage timing, a structured failure report with source context and exact-cause diagnosis, optional local-variable capture with automatic redaction, zero-config nested call tracing, a second output format running alongside the console, and a test suite — without restructuring a single function body. That's the whole idea: story()/stage() wrap what you already have.
